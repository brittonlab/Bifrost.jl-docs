Developing

This page is the source of authority for contributor workflow, extension recipes, and the Monte Carlo Measurements (MCM) compatibility contract. Repository-root files such as AGENTS.md and ARCHITECTURE.md summarize the hard invariants for agent tooling and cross-reference this page.

Development setup

Install Julia and instantiate the project environment as described in the repository README.md (Installation section).

Auxiliary environment (ext/dev-env)

Bifrost is not registered in any Julia registry — the root Project.toml is the package, so julia --project=. -e 'using Pkg; Pkg.instantiate()' works directly there. Everything beyond running Bifrost itself — the notebooks and the documentation build — uses one separate environment, ext/dev-env/ (not a package extension). It resolves Bifrost to this checkout through a [sources] entry, so it instantiates from a fresh clone:

julia ext/dev-env/install_kernel.jl

The script instantiates the environment and installs the checkout-local bifrost Jupyter kernel in which every Julia notebook runs (see ext/dev-env/README.md). test/test_notebook_kernels.jl fails if a Julia notebook names any other kernel. The test suite keeps its own test/Project.toml, which Pkg.test() requires.

When creating, revising, or auditing inline documentation for Julia code, use the julia-docstrings skill (registered at the account/agent level).

Git hooks (required after cloning)

Two pre-commit hooks, configured in .pre-commit-config.yaml, guard every commit:

  • an nbstripout pre-commit hook strips cell outputs — base64 image/HTML blobs and execution counts — from authored notebooks so binary payloads never enter git history;
  • a local commit-msg hook strips Claude Code attribution (session backlinks, bylines, Co-Authored-By trailers) from commit messages.

Neither is active until each clone installs them, so after cloning install the dev dependencies (which include pre-commit) and register both hook stages:

uv sync            # installs the `dev` dependency group, including pre-commit
pre-commit install --install-hooks -t pre-commit -t commit-msg

Because pre-commit installs into .git/hooks/, this repo does not set core.hooksPath. If pre-commit install reports "Cowardly refusing to install hooks with core.hooksPath set", a stale custom hooks path is lingering from an older checkout — clear it with git config --unset-all core.hooksPath, then re-run the install.

Once installed, staged notebooks are stripped automatically on every commit. Stripping is idempotent: committing an already-clean notebook is a byte-level no-op.

.gitattributes is the single source of truth for which notebooks are in scope. The wrapper .githooks/nbstripout-clean.py resolves it with git check-attr and processes only notebooks marked filter=nbstripout-clean, so the pre-commit configuration never restates the scope and cannot drift from it. Third-party notebooks under test/reference-data/ and the legacy notebook under test/legacy-python/ carry no such attribute and are never rewritten.

The wrapper delegates the actual stripping to the upstream nbstripout package, adding one behavior it lacks: a notebook whose outputs are already stripped keeps its original bytes, whatever JSON serialization it happens to use. Plain nbstripout reserializes such a notebook into its own canonical form, which surfaces as a whole-file diff when the notebook was last written by some other tool. The -clean suffix in the attribute name keeps this wrapper's namespace distinct from the filter that nbstripout --install would register, so the upstream tool cannot displace it.

Running the notebook hook by hand

To strip on demand — same wrapper, same scope, same pinned nbstripout the commit hook uses — run it across the whole repository:

uv run pre-commit run nbstripout-clean --all-files --verbose

Running the tests

Run the Julia test suite from the repository root:

julia --project=. test/runtests.jl

This command skips the plot-recipe tests (test/test_plot_recipes.jl): RecipesBase is a weak dependency, absent from the root environment. Pkg.test() — what CI runs — supplies it from test/Project.toml and runs them too:

julia --project=. -e 'using Pkg; Pkg.test()'

Tests are classified by the taxonomy in AGENTS.md (T-PHYSICS, T-VALIDATION, T-SIM-REGRESSION, T-GUARDRAIL, and visual demos); place new tests in one of those categories and follow its standard. Any change that touches an uncertain-input code path must add or extend an MCM test — see Testing MCM changes below.

Building the documentation

Documentation is built with Documenter.jl. Source markdown lives under docs/src/; docs/make.jl defines the build and navigation. A GitHub Actions workflow (.github/workflows/Documenter.yml) rebuilds and deploys the site to GitHub Pages.

Build the docs locally, from the repository root:

julia --project=ext/dev-env -e 'using Pkg; Pkg.instantiate()'
julia --project=ext/dev-env docs/make.jl

The rendered site is written to docs/build/ (open docs/build/index.html).

Code organization

Use this pattern for paired value/derivative quantities in the material, cross-section, and fiber layers:

"""
    _quantity(args...)
    quantity(args...)
    quantity_dω(args...)

Short description of the physical quantity.

`quantity` returns ... in SI units.
`quantity_dω` returns ... in SI units.
"""
function _quantity(args...)
    # Bind local physical symbols explicitly.
    # Compute both the value and derivative from the same nearby expression.
    return (x, x_dω)
end

quantity(args...) = _quantity(args...)[1]
quantity_dω(args...) = _quantity(args...)[2]

The private _quantity method owns the calculation; the public value and derivative accessors are compact tuple selectors. Do not introduce response structs, style-dispatch markers, or derived-quantity bags to carry intermediate physics unless there is a concrete need beyond pairing a value with its derivative. Name derivatives for the differentiated variable (_dω for angular frequency, _dV for normalized frequency); avoid prime notation in public APIs. Document the private implementation and its accessors in one Documenter-compatible block, and state returned SI units directly.

Extending Bifrost

The package is layered with strictly hierarchical dependencies — material ≤ cross section ≤ fiber, geometry ≤ fiber — with the propagation layer consuming callable generators. See ARCHITECTURE.md for the layer-to-file map. Each extension point below names the layer it belongs to. Whatever you add, write code that satisfies the MCM compatibility contract from the start: retrofitting Particles support is much harder than designing for it.

Adding a path segment

Geometry layer (src/geometry/).

  1. Define a struct as a subtype of AbstractPathSegment with a meta::Vector{AbstractMeta} field (and a twist::TwistRate field if it carries mechanical twist), an outer constructor taking the other fields positionally in declaration order plus a meta keyword (field meta, strain and model projection rebuild a segment through it), and a Base.show.
  2. Implement the local-geometry interface tabulated in the AbstractPathSegment docstring — arc_length, curvature, geometric_torsion, position_local, tangent_local, _curvature_vector_local, _parallel_transport_local, _normal_local, _binormal_local, end_position_local, _end_frame_local — in closed form, in the segment's local frame (start at the origin, heading +z).
  3. Declare _length_fields in path-geometry-perturb.jl: the fields an isotropic strain multiplies. The fallback errors, so a forgotten declaration fails loudly.
  4. If the segment's curvature is identically zero, add _segment_is_straight(::YourSegment) = true.
  5. A connector-like segment, whose shape depends on where it is placed, stays unresolved when authored and resolves in _resolve_at_placement(seg, pos, frame_mat), which build calls with the entry position and construction frame. JumpTo is the model: it resolves into a CubicConnector, declares _length_fields(::JumpTo) = (), errors in _scale_length_fields (the fiber strains it by a target-length re-solve), and errors on every geometry query until built.
  6. Add a verb on PathBuilder that appends through _append_segment!, so the segment joins the current spin run, and guardrail tests in test/test_path_geometry.jl.

Adding a birefringence source

Fiber assembly layer (src/fiber/fiber-path.jl).

  1. Define a struct as a subtype of AbstractBirefringenceSource.
  2. Implement generator_K_contribution(source, s) — returns the local 2×2 generator contribution.
  3. Implement generator_Kω_contribution(source, s) — returns ∂K/∂ω. May return a zero matrix if not yet modeled.
  4. Declare coverage_intervals(source) and breakpoints(source). Every source must cover the full fiber domain [s_start, s_end]; gaps are a hard error, not silent zero. The Fiber merges breakpoints globally and the propagator never steps across one.
  5. Extend the fiber-level generator assembly so the new source contributes to K(s) and Kω(s).
  6. Add guardrail tests before physics tests.

Changing the source interface contracts themselves (generator_K_contribution, generator_Kω_contribution) requires user authorization — see AGENTS.md.

Adding a material

Material layer (src/material/).

Define every method in MATERIAL_PROPERTY_API (src/material/material-properties.jl) for the new type, with untyped non-material arguments. A property the model does not cover throws UnsupportedPropertyError (see silica-fluorinated.jl), and a material with no validity restrictions declares runtime_range(::M) = NamedTuple(). A missing method fails precompilation with MaterialAPIError.

Implement _refractive_index(material, λ, T_K) returning (n, n_dω). The public refractive_index(material, λ, T_K) and refractive_index_dω(material, λ, T_K) accessors select the corresponding tuple element. For Sellmeier-form materials the helpers in src/material/material-properties.jl (_sellmeier_index_from_coefficients, _sellmeier_index_from_coefficients_dω, and the _evaluate_sellmeier_* utilities for parameter-dependent coefficients) do the heavy lifting; see silica.jl and germania.jl for worked examples. Routing all spectral evaluation through the Sellmeier helpers also gives Particles compatibility for free; the helpers are branch-free and coercion-free.

Adding a cross section

Cross-section layer (src/fiber-cross-section/).

The base interface lives in src/fiber-cross-section/cross-section.jl; use step-index.jl as the model implementation. A cross section converts material properties into guided-index, dispersion, nonlinearity, and local birefringence response coefficients, and must keep operating wavelength a per-query argument rather than stored state.

MCM compatibility

BIFROST propagates measurement uncertainty with MonteCarloMeasurements.jl (MCM): an uncertain input is a Particles ensemble that flows through the entire computation, so one simulation yields a distribution of outputs. This only works if every function on the path of an uncertain value lifts through Particles. This section is the contract for keeping it that way.

What must lift

Particles may arrive on these inputs:

  • temperature: the user sets uncertainty through the thermal :T_K segment annotation; T_ref_K is a deterministic baseline.

  • bend, twist, tension, and axis-ratio properties,

  • segment shrinkage and field-level MetaAdd/MetaMul perturbations,

  • the per-entry element type of the Jones matrix J and sensitivity G.

The files on those paths — all of src/material/, src/fiber-cross-section/, src/geometry/path-geometry*.jl, src/fiber/fiber-path.jl, and src/path-integral.jl — must obey the rules below on every uncertain-input slot.

The rules

  1. No annotations or coercions that exclude Particles. Particles <: Real but not <: AbstractFloat, so ::Float64 or ::AbstractFloat on an uncertain-input slot silently excludes the ensemble. Leave those slots unannotated. Never coerce with Float64(·) on a path that may carry Particles: promotion does the right thing, coercion destroys the ensemble.
  2. No per-particle branching. A conditional on a Particles value is an error (which branch would the ensemble take?). Either write branch-free code (sign, flipsign, clamp, elementwise arithmetic), or reduce to a representative scalar first and branch on that. The shared reducers live in src/mcm-helpers.jl: use _mcm_pmax for worst-case pmaximum reduction and _mcm_pmean for pmean nominalization. Loop bounds and quadrature limits must be deterministic Float64.
  3. No generic dense linear algebra on Particles matrices. LinearAlgebra.exp (Padé with pivoting), opnorm, and eigvals hit code paths that do not lift. Bifrost.jl implements private variants that work with MCM. For example exp_jones_generator and exp_block_upper_triangular_2x2 (a closed-form Fréchet derivative of the 2×2 exponential) for propagation, and output_dgd_2x2 for DGD extraction (output_dgd uses eigvals and is Float64-only).
  4. Nominalize deliberately, not defensively. Reducing a Particles value to a scalar is correct for control flow (step acceptance, table bisection, Newton iteration counts) but wrong for results — an accumulated phase or coefficient must keep the full ensemble. When you nominalize, say why in a short comment.
  5. Length-changing meta is resolved per lane, not on the breakpoint grid. The breakpoint partition is deterministic Float64 (control flow), but a segment whose physical length is uncertain (:T_K, :tension) must still contribute each lane's full physical length to results. Every lane builds its own scalar geometry, connectors included, and the ensemble generator maps each lane's segment onto the shared nominal grid by the stretch τ_cj = A_cj/L0c (an MCM Particles); see Stages 1 and 3 of The solve workflow. Do not reintroduce a path that integrates over the nominalized segment length only.
  6. No unsafe comparisons. Do not use MonteCarloMeasurements.unsafe_comparisons; tests and library code must make every reduction from Particles explicit at the comparison or control-flow site.

Ensemble-wide adaptive decisions

The adaptive step controller makes one decision per step for the whole ensemble — it cannot take half a step for some particles and a full step for others. _mcm_pmax collapses the error metric via pmaximum, so the worst-case particle drives the step size. That is conservative; a pmean-based reduction is the documented performance compromise if step counts become too large under tight tolerances. _mcm_pmax is the single switch point for that change.

The fiber layer hands the solver an ensemble as lanes (_Lanes, src/ensemble-lanes.jl): one static 2×2 per lane, each advanced by the scalar kernels, with _mcm_pmax taking the worst lane. A Particles-valued generator through the same solver gives the same bits — test/test_mcm_correctness.jl pins it — so a solver kernel stays elementwise and branch-free under both.

Testing MCM changes

test/test_mcm_correctness.jl is the primary MCM suite; thermal, tension, and perturbation coverage also lives in test/test_fiber_thermal.jl, test/test_fiber_tension.jl, and test/test_path_geometry_perturb.jl. When you touch an uncertain-input code path, extend one of these (or add a new MCM test) so the change is exercised with Particles inputs, not just Float64.

Conventions:

  • do not wrap MCM test blocks in MonteCarloMeasurements.unsafe_comparisons;
  • structural invariants ("breakpoints are sorted and deduplicated") should reduce uncertain values explicitly through _mcm_pmean, _mcm_pmax, or a documented nominalized scalar;
  • compare pmean of a Particles result against the nominal Float64 baseline.
